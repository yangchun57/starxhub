## 二、核心机制：与传统 LLM 的本质区别

### 2.1 设计理念

传统 LLM 是"写文章"——逐 token 生成推理过程，再从中解析结论。
**决策模型是"门卫拿清单"**——看一眼输入，直接返回每个选项的概率数字，**零文本生成**。

```
┌─────────────────────────────────────────────────────┐
│  传统 LLM Judge（如 GPT-6 Sol）                      │
│  输入 → 生成推理文本 → 解析结论 → 动作               │
│  耗时：数百ms~数秒 | 成本：按输出token计费            │
├─────────────────────────────────────────────────────┤
│  Decision Model（Microsoft-Decision-1）              │
│  输入 + 选项 → 单次前向传播 → 概率分布 → 直接动作    │
│  耗时：85ms P50 | 成本：输出免费                      │
└─────────────────────────────────────────────────────┘
```

### 2.2 三种问题原语（Question Primitives）

这是该模型的核心 API 抽象，也是接入插件的关键接口：

| 类型 | 语义 | 输入 | 输出 | 典型场景 |
|------|------|------|------|----------|
| **noul** | 是/否判断 | `instructions`（可选 `criteria`） | `0~1` 概率值（yes 的概率） | 门控检测：是否包含 prompt 注入？回复是否承诺退款？ |
| **choice** | 多选一 | `instructions` + `criteria`（选项键值对） | 选中项 + 每项概率分布 | 工单路由、意图分类、工具/Agent 选择 |
| **score** | 有序量表评分 | `instructions` + `criteria`（等级描述列表） | 概率加权平均分 + 每级概率 | 严重性分级、输出质量评分、优先级排序 |

**关键特性：单次请求可包含多个问题**，共享同一个 `state`，一次调用完成路由+分级+标记。

### 3.1 接入渠道

## 五、接入 Cloud Code 插件的可行性分析

### 5.1 适配场景矩阵

| 插件场景 | 适配度 | 说明 |
|----------|--------|------|
| **意图路由** | ⭐⭐⭐⭐⭐ | 用户输入 → choice 分类 → 选择对应 Agent/工具 |
| **输出质量门控** | ⭐⭐⭐⭐⭐ | Agent 输出 → noul 判断是否合格 → 通过/打回 |
| **工单/任务分级** | ⭐⭐⭐⭐⭐ | 任务描述 → score 评分 → 优先级队列 |
| **安全过滤** | ⭐⭐⭐⭐ | Prompt 注入检测、内容安全筛查 |
| **工具选择** | ⭐⭐⭐⭐ | 根据上下文 choice 选择最合适的工具 |
| **多 Agent 调度** | ⭐⭐⭐⭐ | 根据任务类型 choice 分配给最合适的 Agent |
| **代码审查** | ⭐⭐⭐ | 代码质量评分、严重程度分级 |
| **文本生成** | ❌ 不适用 | 该模型不生成文本，不能替代 LLM |

### 5.3 具体接入方案

#### 方案 A：OpenRouter 接入（推荐，最低门槛）

**优势**：
- 无需 Azure 订阅
- API 文档完善（有完整请求/响应格式）
- 兼容 TypeSafe Jev SDK（Python/JavaScript）
- 支持 LiteLLM 等网关代理

**接入代码骨架**：

```typescript
// decision-client.ts
interface DecisionQuestion {
  type: 'noul' | 'choice' | 'score';
  instructions: string;
  criteria?: Record<string, string>;
}

interface DecisionRequest {
  model: string;
  state: string | object;
  questions: Record<string, DecisionQuestion>;
}

class DecisionClient {
  private baseUrl = 'https://openrouter.ai/api/v1/systemone';
  
  async decide(state: string, questions: Record<string, DecisionQuestion>) {
    const res = await fetch(this.baseUrl, {
      method: 'POST',
      headers: {
        'Authorization': `Bearer ${this.apiKey}`,
        'Content-Type': 'application/json'
      },
      body: JSON.stringify({
        model: 'microsoft/microsoft-decision-1',
        state,
        questions
      })
    });
    return res.json();
  }
  
  // 快捷方法：路由决策
  async routeTicket(ticketText: string, teams: Record<string, string>) {
    return this.decide(ticketText, {
      team: {
        type: 'choice',
        instructions: 'Which team should handle this ticket?',
        criteria: teams
      }
    });
  }
  
  // 快捷方法：质量门控
  async checkQuality(output: string, rubric: string) {
    return this.decide(output, {
      passes: {
        type: 'noul',
        instructions: rubric
      }
    });
  }
}
```

#### 方案 B：Microsoft Foundry 直连（企业级）

**优势**：
- Azure SLA 保障
- Entra ID 企业身份认证
- 数据合规（可选 DataZone 区域限制）

**接入前提**：
- 需要 Azure 订阅
- 在 Foundry 门户部署模型获取 endpoint + key
- Foundry API 格式尚未完全公开文档化（截至 10/11 仍缺 Learn 教程页）

### 5.4 接入可行性评估

| 维度 | 评分 | 说明 |
|------|------|------|
| **API 兼容性** | ✅ 高 | 标准 REST + JSON，任何语言可接入 |
| **延迟适配** | ✅ 高 | 85ms P50，适合实时交互场景 |
| **成本效益** | ✅ 极高 | $0.042/M tokens，Agent 工作流中千次调用仅几美分 |
| **SDK 生态** | ✅ 中高 | TypeSafe SDK 兼容，LiteLLM/Portkey 网关支持 |
| **国内可达性** | ⚠️ 中 | OpenRouter 可达（无需 Azure），Foundry 需 Azure 订阅 |
| **文档完备度** | ⚠️ 中 | OpenRouter 端文档完整，Foundry 端文档仍缺失 |
| **模型可控性** | ⚠️ 低 | 权重不公开，仅托管服务；权重持续更新可能导致阈值漂移 |
| **数据安全** | ⚠️ 需评估 | 数据发送至微软服务器，需评估合规要求 |

### 5.5 风险与注意事项

1. **⚠️ 权重漂移**：OpenRouter 注明"weights update continually"，调好的阈值可能随模型更新漂移，需定期重校
2. **⚠️ 非开源**：权重不发布，无法本地部署，完全依赖托管服务
3. **⚠️ 不生成文本**：该模型仅做决策评分，不能替代 LLM 的文本生成能力，需配合使用
4. **⚠️ Foundry API 未完全文档化**：截至 2026-10-11，Microsoft Learn 上仍无完整 how-to 页面
5. **⚠️ 人为决策限制**：官方明确声明不得作为涉及个人决策的唯一依据
6. **⚠️ 国内网络**：需确认 OpenRouter API 在国内的可达性与稳定性

## 七、结论与建议

### 7.1 总体判断

**✅ 可以接入 Cloud Code 插件**，且接入成本较低。

Microsoft-Decision-1 的 API 设计（REST + JSON、三种问题原语、单次调用多问题）天然适合嵌入 Agent 工作流中的决策节点。推荐通过 **OpenRouter** 渠道接入（门槛最低、文档最完整），作为插件的"决策引擎层"。

### 7.2 推荐接入优先级

1. **P0 - 意图路由**：用户输入 → Decision Model → 选择对应处理模块
2. **P0 - 输出质量门控**：Agent 输出 → noul 判断 → 通过/打回重做
3. **P1 - 安全过滤**：Prompt 注入检测、敏感内容筛查
4. **P1 - 任务优先级**：score 评分 → 队列排序
5. **P2 - 工具选择**：根据上下文 choice 最优工具
