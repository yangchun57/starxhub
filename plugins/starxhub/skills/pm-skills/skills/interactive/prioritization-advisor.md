# 优先级顾问（Prioritization Advisor）

## 类型
Interactive Skill

## 用途
根据产品上下文推荐合适的优先级排序框架（RICE/ICE/Kano 等）

## 耗时
30-90 分钟

## 框架原理

不同的产品阶段、团队规模、数据可用性适合不同的优先级框架：

| 框架 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **RICE** | 有数据支撑的成熟产品 | 量化、可比较 | 需要准确数据 |
| **ICE** | 快速决策、数据不全 | 简单快速 | 主观性强 |
| **Kano** | 用户满意度导向 | 区分功能类型 | 需要用户调研 |
| **MoSCoW** | 版本规划、交付导向 | 简单直观 | 粒度粗 |
| **WSJF** | SAFe 敏捷框架 | 考虑延迟成本 | 复杂 |

## 交互流程

### 第一步：上下文收集（问 3-5 个问题）

```
1. 产品阶段？
   - [1] 探索期（0-1，验证 PMF）
   - [2] 成长期（1-10，快速迭代）
   - [3] 成熟期（10-100，稳定运营）

2. 团队规模？
   - [1] 小团队（< 10 人）
   - [2] 中型团队（10-50 人）
   - [3] 大团队（> 50 人）

3. 数据可用性？
   - [1] 数据充足（有用户行为数据、A/B 测试结果）
   - [2] 数据部分（有部分指标，但不完整）
   - [3] 数据稀缺（主要靠直觉和定性反馈）

4. 决策频率？
   - [1] 每周决策（快速迭代）
   - [2] 每两周决策（标准迭代）
   - [3] 每月决策（稳定规划）

5. 利益相关者数量？
   - [1] 少（1-3 人，决策快）
   - [2] 中（4-10 人，需协调）
   - [3] 多（> 10 人，需正式流程）
```

### 第二步：框架推荐

根据回答，推荐 1-2 个最适合的框架，并解释原因。

### 第三步：执行框架

使用推荐的框架对功能列表进行排序。

## 推荐逻辑

```
IF 产品阶段 == 探索期 AND 数据稀缺:
    推荐 ICE（快速决策，不依赖数据）
    
IF 产品阶段 == 成长期 AND 数据充足:
    推荐 RICE（量化比较，数据驱动）
    
IF 产品阶段 == 成熟期 AND 团队规模大:
    推荐 WSJF（考虑延迟成本，适合大团队）
    
IF 决策频率 == 每周 AND 利益相关者少:
    推荐 ICE（简单快速）
    
IF 需要用户满意度导向:
    推荐 Kano（区分基本/期望/兴奋需求）
    
IF 需要版本规划:
    推荐 MoSCoW（Must/Should/Could/Won't）
```

## 框架详解

### RICE 框架

**公式**：RICE = (Reach × Impact × Confidence) / Effort

| 维度 | 定义 | 尺度 |
|---|---|---|
| **Reach**（覆盖范围） | 每季度影响多少用户？ | 绝对数（如 500 用户） |
| **Impact**（影响程度） | 对每个用户的影响有多大？ | 3=大, 2=高, 1=中, 0.5=低, 0.25=极低 |
| **Confidence**（信心） | 对估算的信心有多大？ | 100%=高, 80%=中, 50%=低 |
| **Effort**（工作量） | 需要多少人月？ | 绝对数（如 2 人月） |

**示例**：
```
功能 A：API 限流
- Reach: 2000 用户/季度
- Impact: 2（高）
- Confidence: 80%
- Effort: 1 人月
- RICE = (2000 × 2 × 0.8) / 1 = 3200

功能 B：暗黑模式
- Reach: 5000 用户/季度
- Impact: 0.5（低）
- Confidence: 100%
- Effort: 2 人月
- RICE = (5000 × 0.5 × 1) / 2 = 1250

结论：功能 A 优先级更高
```

### ICE 框架

**公式**：ICE = Impact × Confidence × Ease

| 维度 | 定义 | 尺度 |
|---|---|---|
| **Impact**（影响） | 对目标指标的影响 | 1-10 |
| **Confidence**（信心） | 对成功的信心 | 1-10 |
| **Ease**（容易度） | 实现的容易程度 | 1-10 |

**示例**：
```
功能 A：API 限流
- Impact: 8
- Confidence: 7
- Ease: 9
- ICE = 8 × 7 × 9 = 504

功能 B：暗黑模式
- Impact: 5
- Confidence: 9
- Ease: 6
- ICE = 5 × 9 × 6 = 270

结论：功能 A 优先级更高
```

### Kano 模型

将功能分为 5 类：

| 类型 | 定义 | 策略 |
|---|---|---|
| **Must-be**（基本需求） | 没有会不满意，有也不会满意 | 必须实现 |
| **One-dimensional**（期望需求） | 实现越多越满意 | 尽量实现 |
| **Attractive**（兴奋需求） | 没有不会不满意，有会很满意 | 差异化机会 |
| **Indifferent**（无差异） | 有没有都不在乎 | 避免实现 |
| **Reverse**（反向） | 有了反而不满意 | 绝对不做 |

**调研问题**：
```
1. 如果有这个功能，你的感受？
   - 喜欢 / 理所当然 / 无所谓 / 能忍受 / 不喜欢
   
2. 如果没有这个功能，你的感受？
   - 喜欢 / 理所当然 / 无所谓 / 能忍受 / 不喜欢
```

## 反模式警示

### ❌ 反模式 1：盲目使用 RICE
**问题**：数据不足时强行使用 RICE，导致估算失真
**解决**：数据不足时用 ICE，或先收集数据

### ❌ 反模式 2：忽视信心维度
**问题**：只看 Reach 和 Impact，忽视 Confidence
**解决**：低信心的估算要打折，或标记为"需验证"

### ❌ 反模式 3：一次性排序后不再调整
**问题**：优先级是动态的，需要定期回顾
**解决**：每个迭代回顾优先级，根据反馈调整
