# PRD 开发（PRD Development）

## 类型
Workflow Skill

## 用途
编写结构化的产品需求文档（PRD），覆盖问题定义、用户画像、解决方案、成功指标、用户故事

## 耗时
2-4 天

## 框架原理

PRD 是产品需求的核心文档，连接业务目标和技术实现。好的 PRD 应该：
- **问题驱动**：先明确问题，再讨论方案
- **用户中心**：基于用户画像和场景
- **可衡量**：有明确的成功指标
- **可执行**：包含用户故事和验收标准

## 执行流程

### 第一步：问题定义（30 分钟）

**核心问题**：
1. 我们要解决什么问题？
2. 这个问题有多严重？（量化）
3. 谁受这个问题影响最大？

**输出**：
```markdown
## 一、问题陈述

**当前问题**：
{描述当前的问题，用数据支撑}

**业务影响**：
{量化业务影响，如收入损失、用户流失}

**根因分析**：
{问题的根本原因是什么？}
```

### 第二步：用户画像（1-2 小时）

**核心问题**：
1. 谁是目标用户？
2. 他们的痛点是什么？
3. 他们的使用场景是什么？

**输出**：
```markdown
## 二、目标用户

| 用户角色 | 需求 | 痛点 | 使用场景 |
|---|---|---|---|
| {角色 1} | {需求} | {痛点} | {场景} |
| {角色 2} | {需求} | {痛点} | {场景} |
```

### 第三步：解决方案（2-4 小时）

**核心问题**：
1. 有哪些可能的解决方案？
2. 每个方案的优缺点？
3. 为什么选择这个方案？

**输出**：
```markdown
## 三、技术方案

**推荐方案**：{方案名称}

**方案对比**：
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 方案 A | ... | ... | ... |
| 方案 B | ... | ... | ... |

**技术实现要点**：
1. {要点 1}
2. {要点 2}
```

### 第四步：成功指标（1 小时）

**核心问题**：
1. 怎么衡量成功？
2. 基线是什么？
3. 目标是什么？

**输出**：
```markdown
## 四、成功指标

| 指标 | 基线 | 目标 | 衡量方式 |
|---|---|---|---|
| {指标 1} | {当前值} | {目标值} | {如何衡量} |
| {指标 2} | {当前值} | {目标值} | {如何衡量} |
```

### 第五步：用户故事（2-4 小时）

**核心问题**：
1. 用户需要哪些功能？
2. 每个功能的验收标准是什么？
3. 优先级如何？

**输出**：
```markdown
## 五、用户故事

### US-1：{标题}
```
作为 {角色}，
我希望 {功能}，
以便 {价值}。
```

**验收标准**：
```gherkin
Given {前置条件}
When {操作}
Then {结果}
```

**优先级**：{P0/P1/P2/P3}
**依赖**：{依赖的其他故事}
**预计工期**：{X 周}
```

### 第六步：风险与缓解（30 分钟）

**核心问题**：
1. 有哪些风险？
2. 影响有多大？
3. 如何缓解？

**输出**：
```markdown
## 六、风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|---|---|---|---|
| {风险 1} | {高/中/低} | {高/中/低} | {措施} |
```

### 第七步：交付计划（1 小时）

**核心问题**：
1. 分几个阶段交付？
2. 每个阶段的里程碑？
3. 关键决策点？

**输出**：
```markdown
## 七、交付计划

| 周次 | 里程碑 | 交付内容 | 验收标准 |
|---|---|---|---|
| 第 1 周 | M1 | {内容} | {标准} |
| 第 2 周 | M2 | {内容} | {标准} |
```

## 反模式警示

### ❌ 反模式 1：方案先行
**问题**：先讨论方案，再找问题
**解决**：先明确问题，再讨论方案

### ❌ 反模式 2：指标模糊
**问题**：成功指标不可衡量（如"提升用户体验"）
**解决**：用可量化的指标（如"延迟 < 200ms"）

### ❌ 反模式 3：忽视风险
**问题**：不讨论风险和缓解措施
**解决**：每个 PRD 必须包含风险分析

### ❌ 反模式 4：一次性写完
**问题**：PRD 写完就不更新
**解决**：PRD 是活文档，根据反馈迭代

## 质量检查清单

- [ ] 问题陈述清晰，有数据支撑
- [ ] 目标用户明确，有画像和场景
- [ ] 技术方案有对比，有选择理由
- [ ] 成功指标可衡量，有基线和目标
- [ ] 用户故事符合 INVEST 原则
- [ ] 验收标准可测试（Given/When/Then）
- [ ] 风险分析完整，有缓解措施
- [ ] 交付计划合理，有里程碑
