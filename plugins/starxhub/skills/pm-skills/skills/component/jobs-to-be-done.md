# JTBD 分析（Jobs To Be Done）

## 类型
Component Skill

## 用途
理解客户真正想完成的任务，而非表面需求

## 耗时
10-30 分钟

## 框架原理

JTBD 核心观点：客户不是"购买"产品，而是"雇佣"产品来完成某个任务。

任务的三个维度：
- **功能任务**：想完成什么具体操作？
- **情感任务**：想获得什么感受？
- **社会任务**：想在他人眼中呈现什么形象？

## 模板

```markdown
## JTBD 分析

**用户角色**：{角色}

### 功能任务
当 {触发场景} 时，
用户想要 {完成的操作}，
以便 {达成的目标}。

### 情感任务
用户想要感觉 {期望的感受}，
而不是 {不想有的感受}。

### 社会任务
用户想要在 {他人} 眼中显得 {期望的形象}。

### 当前替代方案
| 方案 | 优点 | 不足 |
|---|---|---|
| {方案 1} | {优点} | {不足} |
| {方案 2} | {优点} | {不足} |

### 痛点与障碍
- {痛点 1}
- {痛点 2}

### 期望成果
- {成果 1}（重要度：高/中/低，满意度：高/中/低）
- {成果 2}（重要度：高/中/低，满意度：高/中/低）
```

## 示例

```
用户角色：产品经理

功能任务：
当需要编写 PRD 时，
用户想要快速生成结构化的需求文档，
以便减少重复劳动，聚焦核心决策。

情感任务：
用户想要感觉专业、高效，
而不是焦虑、手忙脚乱。

社会任务：
用户想要在团队和领导眼中显得专业、有条理。

当前替代方案：
| 方案 | 优点 | 不足 |
|---|---|---|
| 手动写 Word | 灵活 | 耗时、格式不统一 |
| ChatGPT | 快速 | 缺乏结构、不可复用 |

痛点与障碍：
- 每次都要重新组织格式
- 缺乏团队统一的标准
- 无法复用历史经验

期望成果：
- PRD 生成时间 < 30 分钟（重要度：高，满意度：低）
- 格式统一、可复用（重要度：高，满意度：低）
```

## 反模式

- ❌ 只关注功能任务：忽视情感和社会维度
- ❌ 描述产品功能：描述用户想完成的任务
- ❌ 忽视替代方案：了解用户当前如何解决
