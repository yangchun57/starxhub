# 问题陈述（Problem Statement）

## 类型
Component Skill

## 用途
基于证据定义客户问题，避免团队解决错误的问题

## 耗时
10-30 分钟

## 框架原理

好的问题陈述应该：
- **以用户为中心**：描述用户的痛点，不是技术缺陷
- **有证据支撑**：用数据、访谈、观察佐证
- **可衡量**：能量化问题的严重程度
- **不包含方案**：只描述问题，不暗示解决方案

## 模板

```markdown
## 问题陈述

**问题**：{用户角色} 在 {场景} 中面临 {问题}，
导致 {量化影响}。

**证据**：
- {数据 1}
- {访谈引用 1}
- {观察 1}

**影响范围**：
- 影响用户数：{数量}
- 频率：{频率}
- 成本：{金额/时间}

**当前解决方案的不足**：
- {不足 1}
- {不足 2}
```

## 示例

```
问题：中小企业的产品团队在搭建多租户 SaaS 产品时，
需要手动配置数据隔离、权限管理和租户初始化，
导致每个新租户上线需要 1 天，运营成本居高不下。

证据：
- 运营团队每周手动配置 5 个租户，耗时 10 人时
- 30% 的租户配置存在权限错误，需要返工
- 客户反馈签约后等待时间过长（平均 1.2 天）

影响范围：
- 影响用户数：所有新签约客户
- 频率：每周 5 次
- 成本：约 2 人/周的运营成本

当前方案不足：
- 手动配置容易出错
- 无法自助服务
- 缺乏标准化流程
```

## 反模式

- ❌ 包含方案："我们需要一个自动化系统"（只描述问题）
- ❌ 技术导向："数据库缺少索引"（描述用户痛点）
- ❌ 无证据："用户觉得不好用"（用数据支撑）
