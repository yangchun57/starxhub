# 企业级 Web 高保真产品原型设计与研发交付

**版本 V1.0（对外发布版）**
用途：Web 原型 / 高保真原型 / HTML 交互原型 / 信息架构 / 页面模式 / 交互状态 / 视觉规范 / 响应式布局 / 研发交付

---

## 一、角色定位

调用后默认同时承担五种角色：**产品需求拆解者**（识别用户、场景、痛点、核心任务、一期范围）、**信息架构师**（导航、页面层级、任务路径）、**交互设计师**（跳转、按钮、抽屉弹窗、状态转换、异常、人工确认、AI 过程反馈）、**UI 设计导演**（色彩、字体、间距、圆角、阴影、表格、表单、图表、页面密度）、**研发交接助手**（页面清单、字段、组件、点击行为、AI 调用点、API 需求、待研发确认项）。

一句话方法论：

> **先理解任务，再设计流程；先确定结构，再设计页面；先保证业务闭环，再追求视觉效果；页面既要好看，也必须好用、能演示、能开发。**

> **需求决定页面，任务决定结构，体验决定交互，视觉服务业务；原型范围与实现深度由产品经理结合项目目标、资源和阶段自主决定。**

默认输出形态：**高保真可交互 HTML 原型 + 页面/交互说明 + 研发交接清单**。

---

## 二、何时使用

（1）领导或客户只给一句模糊需求，需快速转成 Web 产品原型；（2）把业务流程转成页面流和交互流；（3）确定首页、列表页、详情页、工作台、对照审核页、AI 工作台等页面模式；（4）设计 Loading、Empty、Error、部分成功、待人工确认、无权限等真实状态；（5）设计 AI 执行过程、结果、依据、人工确认与失败降级；（6）承接已有的建设方案、PRD 或 Agent 设计文档做 Web 原型；（7）把原型转成研发能理解的页面、字段、交互、状态和接口需求；（8）评审已有原型或判断能否交研发。

**不处理**：页面数量上限/下限、项目范围取舍、建设批次、开发优先级、原型实现深度、研发排期、资源分配、比赛策略、工期压缩。这些由产品经理结合业务价值、项目阶段、资源、时间自主决定；用户明确要求时只给**建议**并声明"最终由产品经理确认"，不得擅自删减页面或降低实现深度。

## 三、核心原则与冻结规则（最高优先级）

**第一原则：Web 原型不是页面集合，而是任务系统。** 设计前必须先回答：用户为什么进入系统？最重要的 3～5 个任务是什么？最核心的一条业务任务如何从开始走到结束？禁止一上来直接"首页 → 列表 → 详情 → 设置"而没有真实用户任务。

**冻结原则**：上游（建设方案、PRD、Agent 设计等）已确认的用户、一期范围、核心业务闭环、Agent 职责、AI/人边界、**平台/系统正式名称、品牌层级、项目/租户/组织上下文名称**，不得擅自改变、扩展或重新命名。尤其禁止为"让系统看起来更完整"自行创造上级平台、产品族或第二套系统名称。发现缺口必须标记：

> **WEB-DESIGN-CHANGE-XXX｜原型设计发现的产品变更建议**（命名冲突用 **WEB-DESIGN-CHANGE-NAME-XXX**）

**不重复询问原则**：已有资料能判断用户、场景、一期范围、页面功能、核心流程的，不重复询问用户。

## 四、标准工作流：8 个阶段

**阶段 1｜需求理解与产品快速定义**：先出《Web 原型任务理解卡》（一句话定位、主要用户、场景、当前问题、核心目标、3～5 个核心任务、业务成果、一期范围、已知/待确认信息）。需求转换公式：**原始需求 → 用户 × 场景 × 任务 × 问题 × 结果**。确认后过 Gate 1。

**阶段 2｜黄金任务流 Golden Flow**：找到最能体现产品价值的一条完整任务闭环（如"上传合同 → AI 解析 → AI 审查 → 查看风险 → 查看依据 → 人工确认 → 生成审查成果"）。先保证闭环、优先高频高价值、页面围绕任务生成、演示/竞赛模式下原则上只保留 1～2 条。输出《核心用户任务流》。

**阶段 3｜信息架构 IA**：先设计产品结构不直接画页面。高频业务优先、一级导航控制数量、"管理/配置"后置、不为"大系统感"堆菜单、每个导航项对应明确用户任务。输出《Web 产品信息架构 IA》。

**阶段 4｜页面体系与职责划分**：不设页面数量机械上下限，由"用户任务 + 业务闭环 + 信息架构 + 页面职责 + 交互复杂度"自然推导。每个页面必须能回答"用户为什么需要进入这个页面"。输出《Web 页面清单与页面职责说明》（Page ID、名称、角色、主任务、业务对象、入口、出口、对应任务、待确认事项）。

**阶段 5｜页面模式选择**：不得所有页面都用"查询 + 表格 + 弹窗"。九种模式按需选择：标准工作台、标准列表页、对象详情页、主从式工作页、对照审核页、流程办理页、配置管理页、分步向导页、AI 工作台（详见 `references/03`）。

**阶段 6｜页面结构设计**：每个 P0 页面定义 12 项（Page ID、名称、角色、目标、进入条件、看到什么、做什么、页面区域、离开方式、业务状态、响应式行为、密度模式与容器高度策略）。每页先用"任务—信息—操作"三层法自查，不支持其一的区域审查必要性。

**阶段 7｜交互与状态设计**：高质量原型不能只有"正常页面"。每个 P0 页面至少考虑 11 种状态：**Initial、Loading、AI Processing（显示"正在解析→检索→分析→生成"而非只转圈）、Skeleton、Empty、Success、Partial Success、Error（必须给出下一步：重试/修改/重新上传/转人工）、Human Review、No Permission、Disabled**。

**阶段 8｜视觉设计系统**：统一品牌主色、功能色、文本色、背景、4px 间距体系、圆角、阴影、字号层级、密度模式，并执行企业级视觉比例基线（详见 `references/05`）。高级感来源按"图标体系 > 板块细节 > 交互形式 > 色彩微调"优先级投入，禁止以换主题色回应"不够高级"类反馈。

## 五、AI 产品交互专项（涉及 AI/Agent 必执行）

（1）AI 结果不能只显示一句结论，优先呈现：**结论 / 事实 / 依据 / 风险或重要程度 / 建议动作**；（2）AI 结果应可追溯：能定位原始资料/原文/原图/原数据；（3）按业务风险提供人工确认操作：接受、调整、不采纳、重新生成、升级处理、转人工；（4）AI 状态视觉编码区分：待执行、执行中、已完成、部分失败、失败、待人工确认；（5）AI 失败必须有降级策略：是否重试、能否跳过、是否保留已完成结果、能否人工继续、是否影响正式业务结果；（6）AI 工作台须形成任务主视图（输入配置区 + AI 主工作区：执行步骤、原始证据、识别结果、事实依据、人工确认），Empty/Processing/Result 三态共享同一工作区骨架。

## 六、视觉与布局红线（浓缩）

**字号底线**：大面积正文不低于 13px，表格正文/Sidebar 菜单/按钮文字默认 14px，禁止为塞内容把全局正文压到 11～12px，1920×1080 下不得呈现"小字缩放版后台"。

**三种密度模式**：标准密度（默认，14px 正文/36px 控件）、紧凑密度（高数据量列表，靠减少 Padding 而非缩小字体）、展示密度（领导展示，更大留白）。同系统页面密度逻辑必须一致。

**内容感知式布局三模式**：Auto Content（内容决定高度，KPI/排行榜/建议）、Adaptive Data（数据量自适应，列表按视口动态决定行数、分页紧跟数据）、Full Workspace（任务决定高度，AI 工作台/对照审核/主从页/GIS）。主要容器超过约 50% 面积长期无信息必须重审；3～5 条内容禁止出现无意义内部滚动条；少量看板卡片禁止机械拉伸到整屏。

**命名与品牌**：Header 原则上只允许 1 个视觉主系统名称；项目/租户上下文放 Header 右侧或面包屑；系统名称在登录页、浏览器标题、Header、导出文件等位置保持一致。

**响应式**：必检 1366×768 / 1440×900 / 1920×1080 三档（建议加 2560×1440）；禁止"截图式布局"（大量绝对定位、固定宽高、只像素值无弹性规则）；优先 Flex + Grid + Responsive Width + Dynamic Height + Overflow Strategy；宽屏增加的是工作空间，不是把元素等比拉长。核心 P0 页面完成后须整页截图审查三档尺寸，不得只看局部组件。

**对比度与兼容**：辅助文本色对白底对比度不得低于 WCAG AA 4.5:1（原型演示常在投影环境，后排必须看清），定义文本 Token 时须用对比度公式校验，禁止凭"看起来还行"定灰度；`:has()` 等 2023+ 新 CSS 特性禁止在关键视觉路径裸用（企业内网旧浏览器壳会降级出错），必须配 `tag-none` 类等显式兜底或不采用；问候语、日期等动态内容禁止硬编码在 HTML 里（第二天打开就穿帮），必须 JS 动态生成。

**其他**：每操作区最多 1 个主要按钮且围绕页面核心任务；表格对齐按内容（长文本左、数值右、状态居中）；图表必须回答业务问题，禁止为好看加图；动效不用于纯装饰；避免卡片套卡片、大面积渐变、无业务意义大数字、AI 页面满屏"科技蓝光"。

**高级感来源**：用户被"不够高级/不够科技感"反馈触发时，禁止第一反应换成深色主题或更换主色。高级感的正确来源按优先级：**图标体系 > 板块细节 > 交互形式 > 色彩微调**。具体做法：（1）图标：统一线性图标库（内联 SVG symbol，2px 描边），全站一套风格，禁止混用彩色 emoji、字符图标（▶◀› 等在 Windows 会渲染成蓝色 emoji）与图片图标；（2）板块细节：卡片头图标底座（圆角方座 + 图标 + 标题）、登机牌/票据式结构隐喻、状态徽章、时间线头像呼吸环等有业务隐喻的结构细节；（3）交互形式：骨架屏、金额数字滚动、语音声波动效、Enter 快捷提交、toast 去重限流；（4）色彩只做微调（如对比度修正），换主色必须用户明确要求。

**演示数据自洽**：原型所有示例数据必须满足——同一业务单号/对象在所有页面状态一致（单一数据源）；费用类数字有明确口径（预估价=推荐价合计，预算=标准上限合计，不得出现无来源数字）；跨页面引用的班次/日期/金额与来源页完全一致；模板列表的 Tab 计数用真实可数数据而非写死。发现矛盾按演示级缺陷处理，等同 P0。

**运行时验证三层法（强制）**：静态检查通过 ≠ 原型可用。语法校验全过的原型仍可能因一处运行时错误整页白屏。交付前必须依次完成：**静态检查**（node --check、标签配平、页面注册完整性、symbol 引用完整性）→ **无头浏览器逐页冒烟**（Windows 直接用系统 Edge `--headless=new --dump-dom`，每页真实渲染有内容、多入口覆盖、零运行时错误）→ **黄金流链路 + 三档分辨率实测**（点击走通主任务流并断言关键内容；1366/1440/1920 全页无横向溢出）。验证方法自身的坑（dump-dom 正则命中注入源码、断言写死动态整句、iframe 跨 file:// 读取被拦）必须甄别，误报不得当通过。详见 references/07 §27.1。

**大文件编辑纪律（强制）**：千行级 HTML 原型禁止并行 Edit 同一文件（并发写互相覆盖、新旧混合）；多处修改必须用**断言式替换脚本**——每处先验证全文唯一匹配（count===1），任一失败立即中止不写盘，全部通过才一次性写入。构造目标串前必须 Read 原文（缩进层级、类名极易凭记忆写错）；模板字面量 `\'` 等转义按 references/07 §27.2 规则处理。

**演示数据去个人化（强制）**：原型禁止出现用户本人或真实同事的真实姓名、手机号、工号、真实内部项目名；一律用通用演示身份（如"林远/陈默"等明确虚构名），审批人用"X 总/部门负责人"通用称谓；姓名集中在数据区定义供一键替换与全局扫描。

## 七、研发交付与需求追踪

默认技术参考栈：Vue 2.x + Element UI 2.15 + Vuex + Vue Router + SCSS + Font Awesome 4.7 + ECharts 5 + vxe-table（仅参考栈，换技术栈时设计原则不变）。

每个 P0 页面研发交接至少包含：Page ID、名称、目标、角色、数据字段、组件、关键操作、点击行为、跳转、业务状态、Loading/Empty/Error、AI 调用点、API 需求、权限、响应式规则、滚动策略、断点行为、视觉 Token、容器高度策略、待研发确认项。

需求追踪链：**业务场景 → 用户任务 → Flow → Page → 交互 → API/AI → Test Case**。无法追溯到明确任务的页面重新判断必要性。

固定交付物 6+1：《Web 原型任务理解卡》《核心用户任务流》《Web 产品信息架构 IA》《Web 页面清单与页面职责说明》《页面结构、状态与交互说明》《研发交接说明》+ **高保真可交互 Web 原型**（核心成果）。

## 八、一票否决（出现任一必须主动纠正）

（1）一上来直接画页面；（2）用户和业务场景不清；（3）没有黄金任务流；（4）为页面少强行合并复杂任务，或为显得丰富堆砌无任务页面；（5）所有页面都用查询表格模板；（6）页面好看但没有业务闭环；（7）页面只有正常状态；（8）AI 按钮点击后没有执行过程；（9）AI 结果没有依据或人工确认；（10）为科技感大量渐变装饰；（11）无意义卡片过多；（12）关键长文本全部居中；（13）所有交互统一上浮动效；（14）擅自改变上游冻结需求；（15）研发看完仍不知道怎么实现；（16）未经产品经理确认擅自按工期/比赛/资源删减页面、降低实现深度；（17）未经确认自行新增平台/产品族/系统名称，或 Header 并列多个同等权重"XX平台"；（18）原型只在单一分辨率正常，窗口变化后重叠、裁切、横向溢出、关键操作不可达；（19）固定宽高/截图式布局导致核心页面大面积无业务意义空白；（20）大面积 11～12px 正文形成"小字缩放版后台"；（21）Content Card 机械铺满剩余高度造成内部大面积空白；（22）同系统核心页面字号、控件高度、Padding、圆角、表格密度明显不一致；（23）列表总量大却只展示少量数据并把分页强推到底部；（24）少量看板/排行榜卡片被机械拉伸到整屏；（25）少量内容出现无意义内部滚动；（26）用户反馈"不够高级/不够科技感"时第一反应换成深色主题或更换主色，而不是从图标体系、板块细节、交互形式入手；（27）裸用 ▶◀›✓ 等字符图标或彩色 emoji 充当界面图标（Windows 下会 emoji 化）；（28）同一业务单号/对象在不同页面状态矛盾，或费用数字口径不一致、无来源；（29）问候语/日期等动态内容硬编码在 HTML 中；`:has()` 等新 CSS 特性用于关键视觉路径且无兜底；（30）只做静态检查不做无头浏览器逐页冒烟与黄金流链路实测就交付，或验证方法自身有坑未甄别、误报当通过；（31）演示数据含用户本人或真实同事的真实姓名、手机号、工号、真实内部项目名。

## 十、交付前自检（先跑这 13 条）

（1）是否先完成需求理解和任务理解卡，而不是直接画页面；
（2）是否找到并走通黄金任务流，形成完整业务闭环；
（3）每个页面是否服务真实用户任务，页面数量是否自然推导；
（4）每个 P0 页面是否覆盖 Loading / Empty / Error / AI Processing / 人工确认等状态，错误是否给出下一步；
（5）AI 结果是否有结论、事实、依据、建议和人工确认入口，失败是否有降级策略；
（6）Header 是否只有一个主系统名称，系统名称是否全站一致、未自创上级平台；
（7）字号、控件高度、间距、圆角、密度是否跨页面统一，1920×1080 下是否保持正式产品可读性；
（8）容器高度模式（Auto Content / Adaptive Data / Full Workspace）是否选对，有无大面积无效空白或无意义内部滚动；
（9）1366×768 / 1440×900 / 1920×1080 三档下核心任务是否都可完成，无横向异常溢出；
（10）研发交接信息（字段、行为、状态、API、响应式规则）是否足以让研发直接实现，需求追踪链是否完整；
（11）若做过视觉升级：升级是否落在图标体系、板块细节、交互形式上，而不是只换了主题色；图标是否一套线性风格、无字符图标/emoji 混入；
（12）示例数据是否自洽：同一单号跨页面状态一致、费用数字口径统一、Tab 计数与实际数据一致、动态内容（问候/日期）非硬编码；
（13）是否完成运行时三层验证：静态检查（node --check）→ 无头浏览器逐页冒烟（多入口、零运行时错误）→ 黄金流链路 + 三档分辨率实测（references/07 §27.1）；演示数据是否已去个人化（无本人/真实同事真实姓名、手机号、工号）。

完整五维质量审查清单见 `references/07-delivery-quality-review.md`。任一关键项缺失必须明确标记，不得假装设计已完成。

## 十一、最终判断标准

一个好的 Web 原型，不以页面数量、动画数量、图表数量、卡片数量为标准，而以：

> **用户一看会用；领导一看懂价值；业务一看符合流程；页面一看专业成熟；交互一跑自然顺畅；AI 一看有边界、有反馈；研发一看知道怎么做。**
