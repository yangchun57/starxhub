# 0. 一句话方法论

> **先理解移动场景，再设计任务路径；先确定单手主任务，再确定页面；先保证现场可完成、异常可恢复，再追求视觉效果。**

> **移动端设计 = 任务优先 × 少输入 × 强反馈 × 可恢复 × 设备能力 × 网络容错 × 触控友好。**

> **不要把 Web 页面缩小到手机；要把 Web 业务重新组织成移动任务。**

> **移动端正式产品应区分三层：Global Shell（全局壳层）→ Role Home（岗位工作台）→ Task Flow（具体任务流）。Root Navigation 只服务根页面，具体任务页和沉浸页默认退出根导航。**

## 0.1 产品负责人工作 Operating System

本技能 不把“画页面”当起点，而以企业级产品负责人完整工作方式驱动原型。默认遵循以下 12 条：

1. **先业务价值，后功能清单**：先回答为什么做、为谁做、解决什么问题、形成什么业务结果，再决定功能。
2. **先岗位任务，后页面结构**：用户进入移动端是为了完成任务，不是为了浏览菜单。
3. **先业务闭环，后模块拆分**：先把“从发起到完成”的链路走通，再决定首页、列表、详情、表单和工作台。
4. **先对象、状态、证据，后界面**：核心业务对象、状态机、证据链不清楚时，不直接画高保真页面。
5. **先规则与知识，后 AI 包装**：AI 必须建立在业务规则、知识、数据和真实证据上，不用“AI聊天框”冒充智能化。
6. **AI 必须嵌入业务动作**：AI 输出必须能进入确认、派单、整改、审核、复核、归档等真实业务动作。
7. **人工卡口必须清楚**：高风险结论、正式提交、责任认定、审批等场景必须明确人工确认和人工接管。
8. **一期聚焦高价值闭环**：不为“系统看起来完整”把低频、低价值、配置型能力全部塞进一期。
9. **共性能力产品化，项目差异配置化**：优先抽取角色、任务、规则、模板、字段、状态、设备能力等可复用内核，避免每个项目重新做一套。
10. **结果必须可量化**：产品不是“有功能”，而要能对应效率、质量、安全、闭环率、准确率、时效、人工工作量等指标。
11. **资料能判断的不重复问**：优先从已有方案、流程、截图、历史决策和上游 Skill 中自行推导；只有真正影响产品方向且无法推断的信息才向产品经理提问。
12. **先自检再交付**：交付前主动发现并修复逻辑、视觉、适配、状态、返回、弱网和研发落地问题，不把明显问题留给产品经理逐页指出。

一句话概括：

> **业务价值定方向，岗位任务定结构，闭环定流程，对象状态定数据，规则证据定可信度，移动场景定交互，研发约束定落地。**

## 0.2 需求推演主链

面对一句模糊需求，默认按以下链条推演，而不是直接生成页面：

> **背景/目标 → 服务对象 → 岗位 → 场景 → 痛点 → 用户任务 → 业务对象 → 状态变化 → 证据/规则 → AI与人工分工 → 业务闭环 → 结果指标 → 移动任务 → 页面/交互 → API/设备/研发实现**

任何一层发现逻辑断裂，应优先回到上一层修正，而不是用 UI 补洞。

## 0.3 三类闭环必须同时成立

### 业务闭环

例如：

> 发现 → 判断 → 处置 → 复核 → 闭环/升级。

### 数据闭环

至少考虑：

> 原始数据 → 现场证据 → AI/规则判断 → 人工意见 → 处置动作 → 复核结果 → 归档记录 → 后续统计/知识沉淀。

### 产品交付闭环

至少做到：

> 需求 → 原型 → 研发 → 测试 → 现场使用 → 问题/数据回流 → 产品迭代。

如果只完成其中一条，不视为完整企业级产品。

## 0.4 “五层产品模型”

本技能 在画页面前，至少应在内部形成以下五层模型：

1. **价值层**：目标、痛点、结果、指标；
2. **业务层**：岗位、场景、任务、闭环、异常流程；
3. **对象层**：项目、任务、事件、工单、设施、附件等核心对象及关系；
4. **规则数据层**：状态机、字段、证据、规则、知识、权限、来源和留痕；
5. **体验实现层**：移动任务流、页面、交互、设备能力、AI、网络、API、适配和测试。

禁止跳过前四层只做第五层。

## 0.5 业务对象、状态机与证据链

企业级移动产品涉及检查、巡检、审核、审批、整改、采集、AI识别等流程时，必须主动识别：

- 核心业务对象是什么；
- 对象唯一标识是什么；
- 对象从什么状态进入什么状态；
- 谁可以改变状态；
- 改变状态需要哪些前置条件；
- 需要什么现场证据/系统数据/人工意见；
- 是否需要时间、人员、位置、设备、版本等留痕；
- 是否允许撤回、退回、重开、转办、升级；
- 状态变化失败后如何恢复。

高风险或正式业务建议形成：

> **原始数据 → 现场证据 → AI判断 → 规则依据 → 人工意见 → 处置动作 → 复核结果 → 归档记录**

页面只是这条证据链的交互载体，不能反过来替代业务模型。

## 0.6 产品范围与一期取舍

本技能 不机械追求“功能全”。默认按四个问题筛一期：

1. 是否直接支撑黄金任务流；
2. 是否高频或高风险；
3. 是否能形成可验证业务结果；
4. 是否具备当前数据、流程、设备和研发条件。

建议区分：

- **P0**：没有它核心闭环走不通；
- **P1**：明显提升效率、体验或管理价值；
- **P2**：增强项、配置项、低频项、后续扩展项。

除非用户明确要求，原型首先保证 P0 完整，再根据项目目标选择 P1/P2 深度。

## 0.7 企业级产品的“共性内核 + 场景扩展”

当产品面向多个项目、组织、工程类型或岗位时，优先抽取共性：

- 统一身份与权限；
- 统一项目/组织上下文；
- 统一任务框架；
- 统一业务对象与编码；
- 统一状态语义；
- 统一证据与附件模型；
- 统一规则/知识调用接口；
- 统一消息、待办、同步和审计；
- 统一 AI 结果结构与人工确认机制。

差异通过：

> 角色配置、字段模板、规则模板、流程模板、设备能力、场景组件

进行扩展。避免“一个客户一套代码、一个岗位一套产品”。

## 0.8 对领导/客户的产品表达方式

产品方案和原型评审时，优先按以下顺序表达：

> **现在有什么问题 → 谁在什么场景受影响 → 产品如何形成闭环 → 用户怎么操作 → AI/设备在哪里发挥作用 → 最终产生什么结果 → 为什么能落地**

避免：

- 一上来讲技术名词；
- 先展示菜单数量；
- 用“科技感”代替业务价值；
- 用大量功能点掩盖核心流程没有闭环。

## 0.9 AI 产品化原则

涉及 AI/Agent 时，默认检查五件事：

1. **输入证据**：AI 基于什么数据判断；
2. **规则知识**：依据什么规则、规范、知识或历史样本；
3. **过程可见**：用户是否知道 AI 正在做什么；
4. **结果可解释**：结论、事实、依据、置信度/风险、建议是否结构化；
5. **人工可控**：是否能接受、修改、不采纳、重试、转人工，并进入真实业务动作。

AI 的产品价值优先体现为：

> **少输入、少查找、少判断、少重复劳动、更快闭环、更稳定执行规则。**

## 0.10 全局整改与一次性交付原则

当评审发现某类问题，例如：

- 字号偏小；
- 留白异常；
- 卡片过密；
- 页面高度固定；
- Root Navigation 使用错误；
- 按钮遮挡；
- 相同状态样式不一致；
- 360px 下溢出；

不得只修改用户指出的单页。必须：

> **定位问题类型 → 搜索全部同类页面/组件 → 修改设计 Token 或公共组件 → 批量修复 → 多尺寸回归 → 再提交评审。**

同一类低级问题在下一轮重复出现，视为 Skill 执行失败。
