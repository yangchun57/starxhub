# 13. 阶段 7｜移动交互与状态设计

移动产品不能只有正常页面。

每个 P0 页面至少考虑以下状态。

## 13.1 Initial

初始状态。

## 13.2 Loading

加载中。

## 13.3 Skeleton

首次加载骨架屏。

## 13.4 Empty

无任务、无数据、无结果。

必须告诉用户：

- 为什么空；
- 下一步能做什么。

## 13.5 Success

操作成功。

## 13.6 Error

接口、提交、上传、设备调用失败。

必须提供：

- 重试；
- 修改；
- 转人工；
- 稍后同步等下一步。

## 13.7 Offline

离线。

需明确：

- 当前是否可继续；
- 是否保存草稿；
- 哪些能力不可用。

## 13.8 Weak Network

弱网。

建议：

- 降低上传并发；
- 保留本地状态；
- 显示正在重试；
- 避免重复提交。

## 13.9 Uploading

照片/视频/文件上传进度。

## 13.10 Upload Failed

失败后：

- 重试单个；
- 删除；
- 重新选择；
- 保留已成功文件。

## 13.11 Pending Sync

本地已保存、等待同步。

## 13.11.1 统一同步状态语义

弱网现场业务建议统一：

| 状态 | 用户含义 |
|---|---|
| 未创建 | 尚未形成正式本地记录 |
| 本地已保存 | 已保存在设备，可继续编辑 |
| 待同步 | 已进入同步队列 |
| 上传中 | 正在上传证据 / 业务数据 |
| 已同步 | 服务端已确认 |
| 等待重试 | 因网络或服务异常等待再次提交 |
| 数据冲突 | 本地与服务端版本冲突 |

用户界面展示业务语言，不直接暴露：

> retrying / pending_upload / queue_3

等内部技术状态。

## 13.12 Sync Conflict

本地和服务器同时变化。

必须定义：

- 以服务器为准；
- 以本地为准；
- 人工选择；
- 合并。

## 13.13 Permission Denied

摄像头/定位/麦克风权限被拒。

必须给出：

- 说明；
- 再次授权；
- 替代方式。

## 13.14 Device Unavailable

设备不支持 NFC、摄像头异常、定位不可用等。

## 13.15 Draft / Unsaved

未提交草稿。

退出时按风险决定是否提醒。

## 13.16 Disabled

条件不满足时按钮禁用，并说明原因。

# 14. 移动端 AI 交互专项规范

## 14.1 AI流程

推荐移动 AI 黄金流程：

> 采集照片/视频/文本  
> → 校验证据  
> → AI处理  
> → 结构化结果  
> → 用户确认/修改  
> → 提交业务结果。

## 14.2 AI 输入条件

AI按钮必须明确是否可用。

例如：

- 未上传照片 → 禁用；
- 图片质量不足 → 提示重新拍；
- 弱网无法调用云模型 → 保存证据并稍后识别。

## 14.3 AI Processing

不要只显示“AI识别中”。

优先显示：

> 上传证据 → 图像解析 → 识别事实 → 匹配规则 → 生成结果。

## 14.4 AI结果结构

至少包含：

> **结论 / 事实 / 风险等级 / 依据 / 建议动作**

有图像时支持：

> 结果 → 定位原图/框选区域。

## 14.5 人工确认

根据风险可提供：

- 接受；
- 修改；
- 不采纳；
- 重新识别；
- 手工补充；
- 转人工。

## 14.6 AI标记

AI自动填充内容应有来源标记，但不要让“AI”标签抢过业务结论。

## 14.7 AI失败降级

至少定义：

- 是否重试；
- 是否保留照片；
- 是否允许手工录入；
- 是否进入待识别队列；
- 是否影响正式提交。

## 14.7.1 沉浸式智能取证

AI依赖现场画面时，优先采用 Immersive Page：

```text
现场画面
├─ 返回 / 关闭
├─ 当前任务对象
├─ 取景 / 框选区域
├─ 拍摄 / 证据按钮
├─ AI状态
└─ 完成 / 继续采集
```

原则：

- 画面优先；
- 当前项目 / 任务 / 设施仍需可识别；
- 拍摄后进入结构化 AI 结果确认；
- AI框选、标签、置信度按需显示；
- 不用蓝光、扫描线等装饰代替真实状态；
- Immersive Page 不显示 Root Navigation。

## 14.8 移动 AI 的特殊原则

移动端 AI 的价值是：

> **减少现场输入，而不是增加一个聊天框。**

没有明确业务必要时，不要强行加入对话式 Chat UI。

# 15. 移动端设备能力专项规范

## 15.1 摄像头与照片

建议支持：

- 现场拍照；
- 相册选择；
- 图片预览；
- 删除；
- 重拍；
- 上传进度。

图片数量由项目决定。

巡检类场景可参考“多图片，最多 9 张”的现有基线，但不得机械套用所有项目。

## 15.2 图片质量

涉及 AI/证据时建议检查：

- 模糊；
- 过暗；
- 过曝；
- 遮挡；
- 拍摄角度；
- 是否包含目标。

质量不合格应在上传/AI前提示，而不是等后台失败。

## 15.3 定位

支持：

- 自动定位；
- 手工校正；
- 地图选点；
- 定位精度提示；
- 定位失败降级。

禁止假装定位成功。

## 15.4 语音输入

现场长文本适合：

> 文本框 + 语音按钮。

规则：

- 选择器/日期/只读字段不需要语音；
- 录音状态必须明显；
- 识别结果可编辑；
- 权限拒绝后回退键盘输入。

## 15.5 扫码

扫码后应：

> 识别 → 展示对象摘要 → 用户确认 → 进入任务。

不要扫描成功后直接执行高风险动作。

## 15.6 NFC

NFC应有：

- 感应中；
- 成功；
- 未识别；
- 重试；
- 手工搜索。

# 16. 移动表单设计规范

## 16.1 表单布局

默认：

- 单列；
- 标签清晰；
- 高风险字段单独分组；
- 不做 PC 式双列/三列密集表单。

## 16.2 字段三态

统一区分：

### 可输入

用户直接键盘输入。

### 可选择

点击 Picker / Calendar / Bottom Sheet 选择。

### 仅展示

系统自动带出，不可编辑。

三种状态视觉必须不同。

## 16.3 少输入原则

优先级：

> 自动带出 > 选择 > 扫码/定位/拍照 > 语音 > 手工键盘输入。

## 16.4 互斥选项

“正常/异常”“通过/不通过”等二选一：

优先按钮式互斥选择器，提升触控效率。

## 16.5 必填校验

错误提示尽量靠近字段。

提交时：

- 自动滚动到第一个错误；
- 高亮错误；
- 告诉用户怎么修正。

## 16.6 长表单

长表单按业务主题分区。

必要时使用：

- Step；
- 折叠；
- 分步向导。

不要一屏几十个字段。

## 16.7 动态明细

巡检明细、人员、材料等动态列表：

- 新增入口明确；
- 删除二次确认；
- 每条明细有清楚边界；
- 避免嵌套层级过深。

# 17. 导航与顶部区域规范

## 17.1 真实产品与演示原型区分

真实 H5/APP：

- 优先使用宿主/系统状态栏；
- 不机械伪造时间、电量、信号。

演示型 HTML：

- 可以模拟状态栏，用于完整视觉演示；
- 但必须清楚其为 Demo Shell。

## 17.1.1 Preview Shell 与 Product Layout 分离

高保真评审可以使用：

> 390×844 / 430×932 手机预览框。

但生产 H5 / APP 不得把：

```css
width: 430px;
max-width: 430px;
margin: 0 auto;
```

作为真实运行布局规则。

### Demo Preview

允许固定或最大宽度，用于桌面评审、截图和演示。

### Production Runtime

- `width: 100%`；
- 使用真实 viewport；
- 手机宽度自适应；
- 平板单独做布局增强；
- 430px以上设备不应无意义留出左右空白。

结论：

> **Preview Shell ≠ Product Layout**

## 17.2 顶部导航

业务页推荐：

> 返回 | 当前任务 / 页面标题 | 1个必要操作

Root Page 顶部可显示：

> 当前项目 / 当前岗位 / 简短产品身份

但不要每页重复：

> 品牌名 + 完整系统名 + 岗位全称 + 页面标题

建议：

- 正式系统名称在启动页、首页、“我的”等关键位置完整呈现；
- Task Page 优先显示当前任务；
- 岗位信息仅在会影响业务判断时常驻；
- 网络正常状态不常驻顶部。

避免：

- 标题太长；
- 右侧塞3～4个图标；
- 顶部同时承担导航、筛选、网络、岗位和操作过多职责。

## 17.3 Header 与安全区

APP/H5 应适配：

- `env(safe-area-inset-top)`；
- 刘海屏；
- 灵动岛/状态栏区域。
