## 34.2 原型运行时验证 · 三层法（强制）

> **静态检查通过 ≠ 原型可用。** 语法校验、标签配平、路由完整性全部通过的原型，仍可能因生命周期回调里的运行时错误而整页白屏。交付前必须依次完成三层验证，任何一层缺失不得交付。

**第一层｜静态检查（秒级）**

- JS 语法校验：`new Function(scriptText)` 不抛错；
- HTML 标签配平：div/span 等容器标签开闭数量一致；
- 路由完整性：所有 `go('xxx')` / `data-go` / 导航 `data-n` 目标都已注册；
- 引用完整性：所有 `svg('name')` 等组件调用的 name 都已定义。

**第二层｜浏览器逐页冒烟（分钟级）**

用 Playwright（或等价浏览器自动化）真实打开原型，逐页检查：

- 每个页面真实渲染：页面存在、可见、有实际文本内容（innerText 长度 > 阈值），不是空白壳；
- 收集 `pageerror` 与 `console.error`，必须为零；
- **多入口覆盖**：同一页面的所有入口（底部导航 Tab / 侧栏直达 / 首页入口按钮）逐一进入验证，不能只测一个入口。

**第三层｜黄金流链路 + 布局遮挡检测**

- 从第一页点击走通主任务流到最后一页，每步断言关键内容出现（欢迎语、表单按钮、列表项）；
- 布局遮挡检测：底部输入区 / 主操作与 Root Navigation、Safe Area 不重叠，至少两档 viewport（桌面评审壳 + 390 移动）各测一遍。

**实测踩坑的运行时 bug 模式**（静态检查全部查不出来，引以为戒）：

| Bug 模式 | 现象 | 根因 |
|---|---|---|
| `onShow(){this.renderChat()}` | 页面空白壳 | this 指向页面注册配置对象，renderChat 定义在外部对象上，运行时 TypeError。回调内引用外部对象必须用完整限定名 `chatPage.renderChat()` |
| Root 导航 Tab 页漏注册 `root:true` | 进入页面后底部导航消失 | 导航显隐逻辑依赖页面注册时的 root 标志 |
| Root 页自带底部输入条 | 输入框被导航条盖住 | Root 页的底部输入区必须预留 `var(--root-nav-h)` + 安全区高度，规范只讲过 Task 页的互斥，未覆盖「Root 页 + 底部输入」组合 |

## 34.3 浏览器实测环境要点（Windows）

- playwright 未安装时，装到受管隔离工作区（`npm install playwright`，禁止 `-g`）；
- 浏览器内核下载慢或被墙时，直接复用系统 Edge/Chrome：`chromium.launch({ executablePath: 'C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe' })`，无需下载内核；
- `file://` 打开含中文路径必须 URL 编码（`encodeURIComponent`），否则 ERR_FILE_NOT_FOUND；
- 测试脚本按项目保留在受管工作区，不作为一次性产物丢弃——后续每次改版直接复跑回归。

## 34.4 大文件编辑纪律

编辑内嵌模板字符串的 HTML 时：

- 构造 `old_string` 前必须先 Read 目标行段取原文，**禁止凭记忆拼写**（类名、属性名、内联样式极易记错，导致连续编辑失败）；
- 对疑似坏标签先判断是否为合法嵌套（外层 cell + 内层 span 同名闭合是合法的），再决定是否修改；
- 误改后先用 Read 确认实际结构，再决定回滚还是修复，不做叠加猜测式修改。

# 41. 一票否决

出现以下任一情况，本技能 必须主动纠正：

1. 直接把 Web 页面按比例缩小到手机；
2. 不清楚移动用户和使用场景；
3. 没有移动黄金任务流；
4. 首页堆满 PC 菜单；
5. 复杂表格直接横向塞进手机；
6. 卡片一张展示十几个字段；
7. 大面积正文使用10～11px；
8. 点击区域过小；
9. 主操作放在难以触达位置且无必要；
10. 固定底部按钮遮挡内容；
11. 未适配 Safe Area；
12. 键盘弹出后无法提交或看不到输入框；
13. 图片上传失败导致已填表单丢失；
14. 弱网/离线项目没有恢复策略；
15. 权限拒绝后页面死路；
16. AI按钮点后只有旋转图标；
17. AI结果不可编辑、不可确认；
18. AI失败后无法手工继续；
19. 列表没有刷新/加载策略；
20. 根页面、业务页返回关系混乱；
21. 一个页面多个主按钮争抢注意力；

23. 统计看板为了好看堆大量图表；

38. 核心业务对象、状态、证据链互相矛盾；
39. AI 只有入口和结果，没有证据、依据、人工确认与业务动作；
40. 为了体现“智能化”强行增加 Chat UI；
41. 一期同时堆入大量低频配置项，主任务反而不突出；
42. 同一类视觉/适配问题只修用户指出的一页，没有全局整改；
43. 用户已提供或上游已确认的信息仍反复询问；
44. 原型能演示但研发无法确认字段、状态、权限、接口和异常处理；
45. 页面很好看，但无法说明解决了谁的什么问题、产生什么业务结果；
46. 交付前只做静态检查（语法/配平/路由），没有真实浏览器逐页冒烟与黄金流点击链路实测就宣布完成；

48. 演示数据使用用户本人或真实同事的姓名、手机号、工号等真实身份信息。

# 43. 最终判断标准

一个好的移动端原型，不以：

> 页面数量、动画数量、渐变数量、卡片数量

为标准。

而以：

> **用户拿起手机就知道做什么**  
> **现场30秒能完成的事不设计成3分钟**  
> **拍照、定位、语音真正减少输入**  
> **弱网不中断，退出不丢失**  
> **主操作单手能触达**  
> **AI有过程、有依据、可人工修正**  
> **不同手机都能正常使用**  
> **研发一看知道设备、权限、接口和状态怎么实现**

为标准。

# 44.本技能核心公式

> **高质量企业移动端产品 = 业务价值 × 岗位场景 × 业务闭环 × 对象状态与证据链 × 真实移动任务 × 岗位工作台 × 短路径闭环 × 清晰移动IA × Root导航纪律 × 触控友好 × 设备能力 × 完整状态 × 弱网可恢复 × AI人工协同 × 统一视觉 × 多机型适配 × 可研发交付 × 可验证成效**
